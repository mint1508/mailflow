# Deployment

This deployment guide is for the internal cPanel fork. Build from a reviewed Git
commit and keep staging and production in separate Compose projects with separate
secrets and volumes.

## Requirements

- Linux VPS with Docker Engine and Docker Compose 2.21 or newer
- At least 2 vCPU, 4 GB RAM, and 20 GB free disk for the first pilot
- TCP 80 and 443 available for the app reverse proxy
- Outbound access to IMAP 993, SMTP 465/587, and cPanel 2083
- A Cloudflare-managed app hostname such as `inbox.example.com`

## 1. Clone the internal fork

```bash
git clone --branch internal-main https://github.com/mint1508/mailflow.git
cd mailflow
git remote add upstream https://github.com/maathimself/mailflow.git
git fetch --tags upstream
```

Confirm the intended source before every deployment:

```bash
git status --short
git rev-parse HEAD
git describe --tags --always
```

## 2. Generate environment secrets

Generate independent files for staging and production. The script refuses to
overwrite an existing file.

```bash
scripts/deploy/init-env.sh staging staging-inbox.example.com ops@example.com
scripts/deploy/init-env.sh production inbox.example.com ops@example.com
```

The generated `.env.staging` and `.env.production` files have mode `600` and are
ignored by Git. Back them up encrypted because loss of `ENCRYPTION_KEY` makes
stored mailbox credentials unreadable.

## 3. Start staging

```bash
docker compose \
  --env-file .env.staging \
  -f docker-compose.yml \
  -f docker-compose.https.yml \
  --profile https \
  up -d --build
```

This source build pins Node, nginx, PostgreSQL, Redis, and Caddy by digest. It also
bakes the fork commit and upstream baseline commit into version diagnostics.

Only one bundled Caddy instance can bind VPS ports 80 and 443. If the VPS already
has Caddy, nginx, Traefik, or another app on those ports, omit
`docker-compose.https.yml`, bind the Mailflow HTTP port to localhost, and route the
hostname through the existing reverse proxy with WebSocket support and
`X-Forwarded-Proto: https`.

## 4. Validate staging

```bash
docker compose --env-file .env.staging ps
curl -fsS https://staging-inbox.example.com/api/health
curl -fsS https://staging-inbox.example.com/api/version
```

Expected health output contains only `{ "status": "ok" }`. Version output may
contain application version, fork commit, upstream commit, and schema migration;
it must not contain secrets, host credentials, or mailbox data.

Validate in desktop and mobile browsers:

1. HTTPS certificate is trusted and redirects remain on the app hostname.
2. Login creates a secure session and refresh keeps the session.
3. Browser developer tools show `/ws` upgraded with status `101`.
4. The PWA manifest and icons load, and installation is offered on a supported browser.
5. An IMAP test Mailbox can read mail and SMTP can send mail.

## 5. Persistence restart test

Create a disposable app user or setting, then restart without deleting volumes:

```bash
docker compose --env-file .env.staging restart
docker compose --env-file .env.staging ps
```

Confirm the app user, settings, and migration version still exist. Never use
`docker compose down -v` during an update or rollback because `-v` deletes the
PostgreSQL and Redis volumes.

## 6. Promote to production

Repeat staging acceptance on the exact commit intended for production, then:

```bash
docker compose \
  --env-file .env.production \
  -f docker-compose.yml \
  -f docker-compose.https.yml \
  --profile https \
  up -d --build
```

Staging and production must not share `.env` files, PostgreSQL volumes, Redis
volumes, or encryption keys. Use the environment-specific Compose project names
generated by `init-env.sh`.

## Updates

```bash
git fetch origin upstream --tags
git checkout internal-main
git pull --ff-only origin internal-main
docker compose --env-file .env.production build --pull
docker compose --env-file .env.production up -d
```

Record the previous Git commit and take a database/configuration backup before
updating. Follow `docs/phase-0/ROLLBACK.md` if the new schema is not backward
compatible.
